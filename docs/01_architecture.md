# 研究支援・文献引用管理アプリ ― MVP 設計書

> 対象: 第一段階（MVP）機能仕様書 v1
> 作成日: 2026-08-02

## 0. 設計の前提となる決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| プラットフォーム | **Web (PWA) 単体** | スキャン（スマホカメラ）と Word 貼付（PC）の 2 つのシーンを 1 コードベースで賄う。ストア審査不要で反復が速い |
| 引用スタイル内部表現 | **CSL + オーバーレイ層** | プリセットは既存 CSL 資産を流用。独自ルールは後段変換で表現（§4 詳述） |
| 着手順 | 設計 → 引用エンジン → 取込 → UI | 最難関の引用ロジックを先に固める |

### 1.1 ローカルファースト方針

MVP ではサーバを持たない。理由は 3 つ。

1. **仕様書の目的に合致** — 「未発表アイデアの流出リスクを完全に排除」が第一段階の明示的な狙い。データが端末外に出ない設計はこれを構造的に保証する。
2. 認証・課金・インフラ運用のコストがゼロになり、機能開発に集中できる。
3. フェーズ2 の SNS 化時点で同期層を足せばよい（データモデルは §3 で同期を見越した設計にしてある）。

トレードオフ: 端末間でデータが共有されない。スマホでスキャンして PC で書く動線が切れるため、**JSON エクスポート／インポート**を MVP に含めて手動同期の逃げ道を用意する（§7.3）。

### 2.1 バーコード読取の現実的制約

`BarcodeDetector` はブラウザネイティブで高速だが **iOS Safari が未対応**。日本の学生の iPhone 比率を踏まえると、ZXing-js による WASM フォールバックが実質の本線になる。カメラ起動には HTTPS 必須のため、開発時から HTTPS で動かす。

## 3. データモデル

同期を見越し、全エンティティに `id` (UUID)、`createdAt`、`updatedAt`、`deletedAt`（論理削除）を持たせる。

### 3.1 Reference（文献）

CSL-JSON を正とし、アプリ固有情報を外側に持つ二層構造。

```ts
interface Reference {
  id: string;
  csl: CSLItem;              // CSL-JSON 準拠（引用エンジンにそのまま渡せる）
  source: {
    kind: 'isbn' | 'doi' | 'manual';
    identifier?: string;     // ISBN / DOI 原文
    fetchedFrom?: string;    // 'google_books' | 'ndl' | 'crossref'
    fetchedAt?: string;
  };
  projectIds: string[];
  tags: string[];
  createdAt: string; updatedAt: string; deletedAt?: string;
}
```

`csl` を CSL-JSON そのままにしておくことで、citeproc-js への受け渡しに変換が不要になり、将来 Zotero への書き出しも自明になる。

### 3.2 Note（抜き書き・考察）

仕様 3.3-2 の「直接引用の抜き書き」と「自身の考察（間接引用）」を**同一エンティティの型違い**として扱う。検索が横断的である以上、別テーブルに分けると検索実装が二重になるため。

```ts
interface Note {
  id: string;
  referenceId: string;
  type: 'direct' | 'indirect';  // 直接引用 / 間接引用・考察
  body: string;                 // 引用文そのもの、または自分の考察
  comment?: string;             // 直接引用に付ける自分のコメント
  locator?: { page?: string; chapter?: string };  // 引用元ページ
  projectIds: string[];
  createdAt: string; updatedAt: string; deletedAt?: string;
}
```

**`body` と `comment` を分ける理由**: 直接引用の `body` は他人の言葉で、
一字一句変えてはならない。一方 `comment`（なぜ引いたか・どう使うか）は
自分の言葉。同じ欄に書けるようにすると、本文へ転記する際に両者が混ざり
剽窃の温床になる。表示でも背景色と罫線をはっきり変えて区別する。

検索は `body` と `comment` の両方を対象にする。「あの引用に何を書いたか」
から辿れる必要があるため。

`type: 'direct'` の場合、出力時にブロック引用（字下げ）として整形する。`locator` は直接引用でページ番号が必須になるため、警告 UI（§6.2）の対象。

### 3.3 Project（レポート単位）

```ts
interface Project {
  id: string;
  name: string;              // "2026年前期_社会学レポート"
  styleId: string;           // 適用する引用スタイル
  createdAt: string; updatedAt: string; deletedAt?: string;
}
```

スタイルを**プロジェクト単位**で持たせる点が重要。学生は同時期に複数の授業を取り、授業ごとに指定形式が違うため、アプリ全体で1つのスタイルを持つ設計は実態に合わない。

### 3.4 CitationStyle（引用スタイル）

```ts
interface CitationStyle {
  id: string;
  name: string;
  baseCSL: string;           // CSL XML 本体 or プリセット識別子
  overlay?: StyleOverlay;    // 独自ルール差分（§4）
  isPreset: boolean;
}
```

## 4. 引用エンジン ― 本設計の中核

### 4.1 課題の所在

仕様 3.2-2 は「ユーザーがダミー出力を編集すると、システムが差分を解析して独自フォーマット規則として保存・適用する」と定める。これは**例からのプログラム合成**であり、素朴に実装すると破綻する。

具体例で示す。`田中，佐藤，加藤` → `田中ほか` という編集ひとつを与えられたとき、考えうる規則は少なくとも以下がある。

- 著者が 3 名以上なら 1 名目 + 「ほか」
- 著者が 2 名以上なら 1 名目 + 「ほか」
- 文字列 `，佐藤，加藤` を `ほか` に置換
- 2 名目以降を「ほか」に置換

**単一の例から規則は一意に定まらない。** これが実装上の本質的な困難であり、仕様書のままでは実装できない箇所。

### 4.2 解法 ― 多例同時提示による規則の確定

ダミーデータを**単一ではなく行列として提示**し、パターン間の差分から規則を確定させる。

ユーザーに提示する編集画面:

```
■ 和文・書籍
 著者1名   田中太郎（2020）『社会学入門』岩波書店．
 著者2名   田中太郎・佐藤花子（2020）『社会学入門』岩波書店．
 著者3名   田中太郎・佐藤花子・加藤次郎（2020）『社会学入門』岩波書店．
 著者5名   田中太郎・佐藤花子・加藤次郎・鈴木一郎・高橋実（2020）…

■ 欧文・雑誌論文
 著者1名   Smith, J. (2020). Title of article. Journal Name, 12(3), 45-67.
 著者3名   Smith, J., Brown, K., & Lee, M. (2020). …
```

ユーザーが「著者3名」の行だけを `田中太郎ほか（2020）…` に直せば、「著者1名・2名は変更なし、3名以上で省略」という規則が**差分の有無から確定する**。推論すべき対象が有限のパラメータ集合に縮小される。

### 4.3 StyleOverlay の構造

推論結果は CSL XML ではなく、以下の限定されたパラメータ集合として保存する。

```ts
interface StyleOverlay {
  authors?: {
    etAlMin?: number;          // 何名以上で省略するか
    etAlUseFirst?: number;     // 省略時に何名残すか
    etAlTerm?: string;         // "ほか" / "et al." / "他"
    delimiter?: string;        // "・" / "，" / ", "
    lastDelimiter?: string;    // "・" / ", & "
    nameOrder?: 'family-given' | 'given-family';
    initializeGiven?: boolean; // 名を頭文字化するか
  };
  date?: {
    wrapper?: [string, string];  // ["（", "）"] / [" (", ")"]
    yearOnly?: boolean;
  };
  title?: {
    wrapper?: [string, string];  // ["『", "』"] / ["", ""]
    emphasis?: 'italic' | 'none';
  };
  fieldOrder?: string[];       // ["author","date","title","publisher"]
  terminator?: string;         // "．" / "."
  separators?: Record<string, string>;
}
```

**設計判断**: CSL XML を直接書き換えるのではなく、citeproc-js が生成した出力に対して**後段で変換を適用する**。これにより逆推論の対象が上記の数十パラメータに限定され、実装可能性が担保される。

トレードオフ: CSL の表現力すべてはカバーできない。極端に特殊な大学ルールには対応できないケースが残る。その場合の逃げ道として、**プレビュー結果を最終的に手編集できる**導線を用意する（完全な自由度は手編集で確保）。

### 4.4 推論アルゴリズム

```
入力: ダミー出力（システム生成）と編集後テキスト（ユーザー入力）のペア群
1. 各ペアをトークン列に分解（著者/年/書名/出版社/区切り記号）
   ※ 生成側が各フィールドの位置を記録しているため、分解は
     文字列解析ではなくスパン照合で行える（これが精度の鍵）
2. フィールド単位で差分を取る
3. 差分パターンを StyleOverlay のパラメータへマッピング
4. 推論結果を全ダミー行に再適用し、ユーザー編集結果と一致するか検証
5. 不一致があれば該当行をハイライトし、ユーザーに再編集を促す
```

ステップ 1 が精度の鍵。ダミー生成時に「この文字範囲は著者フィールド」というスパン情報を保持しておけば、編集後テキストとの照合が単なる文字列マッチングではなくなり、誤認識が激減する。

ステップ 4 の**検証ループ**が品質保証の要。推論が外れていればユーザーに即座に見える。

## 5. 外部 API 連携 ― 検証済み

> 2026-08-02 実測。§5.4 に検証結果を記載。

### 5.1 ISBN → 書誌情報

| API | 用途 | CORS | 判定 |
|---|---|---|---|
| 国立国会図書館サーチ | **和書の第一候補** | `*` | 採用 |
| Open Library | 洋書の第一候補 | `*` | 採用 |
| Google Books | — | 反射 | **不採用**（§5.4-b） |

**フォールバック順**: NDL → Open Library → 手入力

和書中心の人文・社会科学が主対象である以上、NDL を第一候補にする点は重要。実測で和書カバー率は **NDL 9/10 に対し Open Library 2/10**（§5.4-c）。逆に洋書は Open Library が確実に引ける。**ISBN の先頭が `978-4`（日本）かどうかで問い合わせ先を切り替える**のが最も素直な実装になる。

### 5.2 DOI → 論文メタデータ

Crossref REST API (`https://api.crossref.org/works/{doi}`) を使用。CORS は `*` で開放されており、ブラウザから直接利用できる。

**制約**: "polite pool"（User-Agent に連絡先を入れるとレート制限が緩和される運用）は**ブラウザから利用できない**。プリフライト応答の `access-control-allow-headers` に `User-Agent` が含まれておらず、そもそもブラウザは User-Agent の上書きを禁止しているため。したがって匿名プールでの利用となる。学生1人あたりの利用頻度では実用上問題ないと判断するが、混雑時の 429 に備えたリトライ処理は入れる。

### 5.3 CORS の結論

**NDL・Crossref・Open Library はいずれもブラウザから直接叩ける。プロキシは不要で、§1.1 のサーバレス構成は維持できる。**

### 5.4 検証で判明した重要事項

**a. NDL は読み仮名を返す（設計上の朗報）**

実測レスポンスに以下が含まれる。

```
dc:creator                 = 小磯, 修二 / 村上, 裕一, 1981- / 山崎, 幹根, 1967-
dcndl:titleTranscription   = チホウ ソウセイ オ コエテ : コレカラ ノ チイキ セイサク
dcndl:creatorTranscription = コイソ, シュウジ / ムラカミ, ユウイチ
```

著者が**姓名分割済み**で、かつ**読み仮名が取れる**。§7.1 で懸念した「50音順ソートの破綻」は、NDL 由来の和書については発生しない。読み仮名の手入力補完 UI は優先度を下げてよい。

**b. Google Books は API キーなしでは使用不可**

全エンドポイントで恒常的に HTTP 429。レスポンス本文は「共有プロジェクトの1日あたりクォータ枯渇」を示しており、時間をおいても回復しない。キーなし利用は事実上閉じられている。MVP では採用しない。

**c. 和書カバー率の実測（人文社会系10件）**

| | NDL | Open Library |
|---|---|---|
| ヒット | **9/10** | 2/10 |

Open Library が引けたのは東大出版会・人文書院の2件のみ。岩波・講談社・ちくま・みすず等の主要人文書はヒットしない。**和書で Open Library に頼る設計は成立しない。**

**d. Open Library の精度は ISBN が正しい限り良好**

書名検索 → ISBN 取得 → 再取得の往復テストで 4/4 正確（Butler, Latour, Said, Bourdieu）。ただし癖がある。

- **版・言語が揺れる**: Said *Orientalism* を引くとポルトガル語版 *Orientalismo* が返るケースがあった。ISBN が版を一意に決めるため原理的には正しい挙動だが、ユーザーの意図した版と異なる可能性がある
- **書名が全角大文字で入っている**レコードがある（`REASSEMBLING THE SOCIAL: AN INTRODUCTION...`）。引用出力前に正規化が要る
- `publish_date` が `June 1, 2006` のような自由書式。**年の抽出処理が必須**

**e. 取得結果は必ずユーザー確認を挟む**

上記 d の通り、API が返す書誌は「ヒットした＝正しい」とは限らない。取込直後に**確認画面を挟み、ユーザーが版・年を目視修正できる導線**を必須とする。誤った書誌のまま引用リストが生成されると、ユーザーは気づかないまま誤りを提出することになるため、ここは省略してはならない。

## 6. 主要 UI

### 6.1 画面構成

```
[取込]  スキャン / DOI 貼付 / 手入力
[書架]  全文献一覧・横断検索
[文献詳細] 書誌編集 + プレビュー + ノート
[プロジェクト] 振り分け・並び替え・出力
[設定]  引用スタイル管理・独自ルール編集
```

### 6.2 リアルタイムプレビューと警告 UI（仕様 3.3-1）

編集画面の下部に、**プロジェクトに設定されたスタイルで整形した結果**を常時表示。

警告の階層:

| レベル | 条件 | 表示 |
|---|---|---|
| エラー（赤） | 著者・タイトル・出版年のいずれかが空 | 該当フィールド枠を赤、プレビュー上で `[著者不明]` |
| 警告（黄） | 直接引用ノートがあるのにページ番号が空 | 黄色ハイライト |
| 情報（灰） | 出版地・版次など任意項目が空 | 控えめな表示 |

**設計判断**: 警告は「引用として成立するか」を基準に階層化する。すべて同じ強さで警告すると無視されるようになるため、必須項目とそうでないものを明確に分ける。

### 6.3 横断検索（仕様 3.3-2）

書誌（タイトル・著者）と Note の本文を単一の検索窓で横断。日本語の全文検索には形態素解析が要るが、MVP では **bigram インデックス**で妥協する（Dexie 上に自前構築）。精度は形態素解析に劣るが、辞書配布のコスト（数 MB の初回ダウンロード）を回避でき、学生の文献数規模（数百件）なら十分実用になる。

## 7. 出力機能

### 7.1 自動整列（仕様 3.4-1）

和文・欧文の混在リストの並び順は、スタイルによって規則が異なる。

- 和文: 50音順（読み仮名が必要 → NDL API は読み仮名を返すため、これを保持する）
- 欧文: アルファベット順
- 混在時: 和文→欧文 の順が日本の慣行として一般的（スタイル設定で切替可能にする）

**検証済み**: NDL は `dcndl:titleTranscription` / `dcndl:creatorTranscription` で読み仮名を返す（§5.4-a）。和書は NDL を第一候補にする設計のため、50音順ソートは自動的に成立する。

ただし NDL でヒットしない和書（実測 10件中1件）は手入力になり読み仮名が欠落するため、**読み仮名フィールドを手で補える UI** は残す。優先度は中。

### 7.2 リッチテキストコピー（仕様 3.4-2）

`navigator.clipboard.write()` で `text/html` と `text/plain` の両方を ClipboardItem に載せる。これにより Word / Google ドキュメントには書式付きで、プレーンテキストエディタには素のテキストで貼り付く。

斜体（欧文誌名等）、ぶら下げインデント、ブロック引用の字下げを HTML + インライン CSS で表現する。

**既知の制約**: Safari は `clipboard.write()` をユーザー操作起因のイベントハンドラ内でしか許可しない。非同期処理を挟むと失敗するため、**HTML 生成をクリック時点で同期的に完了させる**実装が必要。

### 7.3 エクスポート

| 形式 | 用途 | 仕様 |
|---|---|---|
| `.txt` | 汎用・バックアップ | 仕様 3.4-3 |
| `.json` | **端末間の手動同期** | 仕様外だが §1.1 の制約を埋めるため MVP に含める |

### 9.2 実装上ハマった点と対処

**a. CSL は language の「値」で分岐できない**

`<if variable="language">` は値ではなく**存在の有無**しか判定しない。和文/欧文で書式を
切り替える APU 形式では致命的。当初 `genre` に `ja` を立てて回避したが、**APA が genre を
`[Ja]` として出力に表示してしまう**副作用が判明。実測で各フィールドを調べ、APA・SIST 02
のいずれも出力に使わない **`annote`** をフラグ置き場に採用した。

**b. citeproc は不可視の特殊文字を混ぜる**

出力に U+202F（narrow no-break space）や U+00A0 が混入し、ページ範囲のハイフンは
en dash (U+2013) に変換される。見た目はほぼ同じだが Word 上では別文字として残り、
検索・置換や文字数カウントが狂う。`sanitizeSpacing()` で通常文字へ均す。

**c. ja-JP ロケールの語が欧文側に漏れる**

`and="text"` は既定ロケール（ja-JP）の「と」を拾い、`Maurer, P.C.とYao, N.Y.` になった。
欧文著者は `and="symbol"` を明示する。

**d. SIST 02 の巻号ラベル**

公式 CSL は `term="volume" form="short"` を使い、ja-JP ロケールが「巻」「号」「ページ」と
解決する。SIST 02 の規定は `vol.` / `no.` / `p.` なので、**公式 CSL 本体には手を入れず
スタイル内 `<locale>` で上書き**した。

**e. 50音順は citeproc に任せられない**

漢字のコードポイント順は 50音順と一致しない（「山崎」「小磯」がコード順では逆になる）。
citeproc の `<sort>` を使わず、**読み仮名を持つアプリ側（`sort.js`）で並べ、
`renderBibliography(..., { preserveOrder: true })` で順序を保持**する設計にした。
読み仮名は NDL の `dcndl:creatorTranscription` 由来（§5.4-a）。欠落文献は
`findMissingReadings()` で検出し UI で補完を促す。

**f. 数値文字参照が Word にそのまま出る**

citeproc は `&` を `&#38;` として出力する。これを残したまま貼り付けると Word 上に
`&#38;` と表示されるため、リッチテキスト化の際に実文字へ戻す（`<` `>` はタグ誤認を
避けるため据え置き）。

## 9.5 取込機能 実装記録（2026-08-02）

DOI（Crossref）・ISBN（NDL / Open Library）の取込を実装。`importByIdentifier()` が
入力から DOI / ISBN を自動判別して振り分ける。

### 実データで判明した重要な癖

**a. Crossref は和文論文の `title` を空にする（最重要）**

和文論文は `title: [""]` で返り、**実際の日本語タイトルは `original-title` に入る**。
`title` だけを読む実装だと和文論文のタイトルが空欄で取り込まれる。人文社会科学が
主対象である以上、致命的な欠陥になるところだった。`title` が空なら
`original-title` にフォールバックする。

**b. Crossref は author を null にすることがある**

書評論文などで著者情報が未登録。`validateItem()` の警告で捕捉し、確認画面で
手入力を促す。

**c. NDL は訳書の原著者と訳者をまとめて `dc:creator` に入れる**

`dc:creator` = [Bauman Zygmunt, 奥井智之] のようになる。`<author>` タグには
役割表記（「〜 著」「〜 訳」）が入っているため、これを手掛かりに
`author` / `translator` へ振り分ける（`parseCreatorRoles()`）。

**d. NDL の読み仮名は著者と同数・同順とは限らない**

上記の訳書では creator 2件に対し `creatorTranscription` は「オクイ, トモユキ」1件のみ
（欧文名には読みが付かない）。**添字で対応付けると別人の読みを割り当ててしまい
50音順が壊れる**。件数が一致するときだけ対応付け、しない場合は破棄して
UI での手動補完に回す。

**e. 和文書誌でも筆頭著者が欧文名のことがある**

訳書の原著者など。ローマ字表記を 50音順の中に混ぜると並びが不自然になるため、
ソート時は欧文ブロック側へ回す。

### 追加した書式

APU マニュアルに訳書の規定はないが、訳者を落とすと書誌として不正確になるため
`著者（年）『書名』訳者訳，出版社.` の形を補った。

## 9.5 DOI 取込の実装記録（2026-08-02）

実装: `src/import/crossref.js`

### a. Crossref は和文論文のタイトルを `title` に入れない

**最重要の発見。** 和文論文は `title` が空文字 `[""]` で、実際の日本語タイトルは
`original-title` に入る。

```
DOI: 10.7129/jject.10.169
  title          : [""]                                        ← 空
  original-title : ["小内透著『戦後日本の地域社会変動と地域社会類型』"]  ← 実体
  author         : null
```

`title` だけを読む素直な実装では、**和文論文の取込でタイトルが空欄になる**。
人文社会科学が主対象である以上これは致命的なので、`title` が空なら
`original-title` にフォールバックする。`container-title` も同様に
`original-container-title` を見る。

### b. 和文誌は著者情報を持たないことがある

同じレコードで `author: null`。和文誌が Crossref に著者を登録していない
ケースが実在する。取込後に手入力が必要になるため、警告 UI（§6.2）で
明示する。

### c. 著者が空だとタイトルが著者位置へ繰り上がる

CSL の `substitute` 既定動作により、著者不在時にタイトルが著者位置へ移動し、
**本来のタイトル位置が空になって書誌が壊れる**（`『』` も外れる）。

`<substitute><text value="著者名不明"/></substitute>` では解決しない
（citeproc は substitute 内の固定文字列を無視する）。**正規化層で
`author: [{literal:'著者名不明'}]` を実データとして補う**方式を採った。
`_authorUnknown` フラグを立て、UI 側で「著者を補ってください」と促せるようにする。

### d. DOI 入力のゆらぎ吸収

学生は DOI を様々な形で貼り付ける。`extractDoi()` で以下を吸収する。

| 入力 | 抽出結果 |
|---|---|
| `10.1086/227049` | `10.1086/227049` |
| `https://doi.org/10.1086/227049` | `10.1086/227049` |
| `doi:10.1086/227049` | `10.1086/227049` |
| `本文中に 10.1086/227049。` | `10.1086/227049` |

末尾の句読点・括弧は落とす（貼り付け時に混入しやすい）。

### e. 検証済みの動作

- 欧文論文（社会学・自然科学）: 著者・巻号・ページとも正確
- 和文論文（`title` 空・`author` null）: タイトル復元と著者補完が機能
- 存在しない DOI: `404` を「この DOI は見つかりませんでした」として返す
- 429/5xx: リトライ後にユーザー向けメッセージを返す

### f. 残る制約

Crossref は和文誌の**雑誌名を英語表記でしか持たないことがある**
（例: `Contemporary Sociological Studies`）。和文論文なのに雑誌名が英語で
出力されるため、ユーザーが手で直す必要がある。取込確認画面（§5.4-e）で
編集できるようにする。

## 9.6 ISBN 取込の実装記録（2026-08-02）

実装: `src/import/isbn.js`、統合層 `src/import/index.js`

### a. 振り分け方針

ISBN の先頭で問い合わせ先を決め、空振りしたらもう一方へフォールバックする。

| ISBN | 第一候補 | 第二候補 |
|---|---|---|
| `978-4` / `979-4` / `4`（和書） | NDL | Open Library |
| その他（洋書） | Open Library | NDL |

和書で NDL を優先するのはカバー率（実測 9/10 対 2/10）に加え、**読み仮名が
取れるのが NDL だけ**だから（50音順ソートの前提、§5.4-a）。

### b. NDL は責任表示を description の中に文字列として持つ

訳書の原著者と訳者を分けるには役割表記が要るが、`dc:creator` は両者を
区別せず並べる。

```
dc:creator = Bauman, Zygmunt, 1925-2017 / 奥井, 智之, 1958-
```

役割は `<author>` および `<description>` 内の責任表示にある。

```
責任表示：ジグムント・バウマン 著,奥井智之 訳
```

**注意**: この責任表示は `<description>` の中に HTML 断片が
**エスケープされた文字列**として入っており、`<li>` は XML 要素ではない。
`getElementsByTagName('li')` では取得できず、文字列として正規表現で
抜き出す必要がある（実測で確認）。

### c. NDL の人名には生没年が混入する

`村上, 裕一, 1981-` / `Bauman, Zygmunt, 1925-2017` のように生没年が付く。
書誌情報ではないため除去する。除去しないと引用文に `1981-` が出る。

### d. 読み仮名は著者と同数・同順で返るとは限らない

訳書では原著者（欧文名）に読みが付かず、訳者の分だけ返ることがある。

```
dc:creator                 = [Bauman Zygmunt, 奥井智之]   (2件)
dcndl:creatorTranscription = [オクイ, トモユキ]            (1件)
```

添字で対応付けると**別人の読みを割り当てて 50音順が壊れる**ため、
件数が一致するときだけ採用し、しなければ破棄する。破棄した生の読みは
`transcription.authorsRaw` に残し、UI での手動補完の候補として使う。

### e. 検証済みの動作

| ケース | 結果 |
|---|---|
| 和書・3名共著（ハイフン付き ISBN） | 著者3名＋読み仮名を取得 |
| 和書・訳書 | 原著者と訳者を分離、読み仮名は安全に破棄 |
| 和書・単著 | 正常 |
| 洋書（Open Library） | 正常 |
| 存在しない ISBN | 「手入力で登録してください」を返す |

引用出力例（APU 形式）:

```
小磯修二・村上裕一・山崎幹根（2018）『地方創生を超えて : これからの地域政策』岩波書店.
Bauman, Zygmunt（2017）『コミュニティ : 安全と自由の戦場』奥井智之訳，筑摩書房.
```

### f. 残る課題

- ~~訳書の原著者が欧文名のまま和文ブロックに出る~~ — **§9.18-a で確定**
  （「ルーマン, N.」と読点で区切る）。
- NDL は `dcterms:issued` に `2018.7` と月まで持つが、現在は年のみ採用。
  APU 形式は年のみで足りるため実害はない。

## 9.7 永続化層の実装記録（2026-08-02）

実装: `src/db/schema.js`（スキーマ・bigram）、`src/db/repository.js`（データアクセス）

### a. スキーマ

```
references: id, createdAt, updatedAt, deletedAt, *projectIds, *searchIndex
notes:      id, referenceId, type, createdAt, updatedAt, deletedAt, *projectIds, *searchIndex
projects:   id, name, createdAt, updatedAt, deletedAt
settings:   key
```

`*` は多値インデックス。`*searchIndex` が bigram 検索の、`*projectIds` が
プロジェクト振り分け（仕様 3.3-3）の基盤になる。

### b. 全文検索は bigram + 検証の二段構え

日本語は空白で語が区切られないため前方一致では実用にならない。形態素解析器は
辞書が数 MB あり初回ロードが重いので、MVP では 2 文字組（bigram）の多値
インデックスを使う。

**重要**: bigram インデックスは「その 2 文字を含む」候補を返すだけで語順を
保証しない。索引だけで結果を返すと「共同性」の検索に「性同共」が当たる。
そのため**候補を絞ったあと元テキストへの部分一致で必ず検証する**。
実測で語順違いが 0 件になることを確認済み。

### c. 索引と検証の対象は必ず揃える

`referenceBigrams()`（索引作成）と `search()` 内の `refText()`（検証）は
同じフィールドを並べる必要がある。片方だけにフィールドを足すと、
索引には当たるのに検証で落ちる（またはその逆）という気づきにくい不具合になる。

### d. 訳書の原著者が検索で引けない問題

NDL は訳書の原著者を **`Bauman, Zygmunt`（欧文表記）** で返すため、
索引には `ba` は入るが「バウ」は入らない。日本語話者は「バウマン」で
探すので引けなかった（実測で発覚）。

責任表示には**カタカナ表記**（`ジグムント・バウマン 著`）があるので、
これを `transcription.displayNames` として保持し、検索索引に含めることで解決した。

### e. 保存経路の集約

検索インデックスの更新漏れは「検索結果の欠落」として現れ、しかも
気づきにくい。そのため `Repository` に保存を集約し、bigram の再構築を
保存処理の内側で必ず行う。呼び出し側が索引を意識する必要はない。

### f. バックアップ（設計書 §7.3）

サーバを持たない構成のため、端末間の移動は JSON エクスポート／インポートが
唯一の手段になる。取り込み時は**索引を必ず作り直す**（エクスポート元の
実装バージョンに依存させない）。

検証済み: 端末A → JSON → 端末B の往復で文献・ノート・プロジェクトが
再現し、取り込み先で検索も動作する。`merge` / `replace` の両モード、
不正ファイルの拒否も確認。

### g. 一気通貫の動作確認

「プロジェクト作成 → ISBN/DOI 取込 → 振り分け → 抜き書き記録 →
横断検索 → 引用文献リスト生成 → バックアップ」を通しで実行し、
すべて期待通り動作することを確認した（`test/e2e.mjs`）。

という目的の中核。現状は ISBN の手打ちが必要で、仕様の狙いを満たしていない。

### d. その他の弱点

- **オフライン時の挙動が未検証**。`fetch` の失敗は握っているが、PWA として
  のオフライン動作（Service Worker）は未着手
- **エラー時のリカバリが弱い**。取込に失敗した場合、手入力で登録する導線が

  実測していない

## 9.9 取込動線の変更（2026-08-02）

実装: `src/import/search.js`

### a. 主動線を「著者名・タイトル」に変更

ISBN / DOI は**手元に現物がある場合しか使えない**。実際の利用場面は
「あの本を入れたい」という状態から始まることが多いため、著者名と
タイトルによる検索を主動線に据え、コード入力は `<details>` に畳んだ。

| 経路 | 位置づけ | API |
|---|---|---|
| 著者名・タイトル検索 | **主** | NDL OpenSearch / Open Library Search |
| ISBN・DOI | 副（折りたたみ） | NDL / Open Library / Crossref |
| 手入力 | 最終手段（折りたたみ） | — |

### b. NDL は雑誌記事・講演録も返す

「地方創生を超えて」で検索すると、目的の書籍は**3件目**に埋もれ、
上位2件は講演録と座談会記事だった。`mediatype` パラメータでは絞れない。

`<category>` が「図書」「記事」を持つのでこれで判別し、
図書 > 出版社あり > ISBN あり の順で加点して並べ替える。記事を除外
しないのは、論文を探している場合もあるため。

種別の加点（図書 +10）と減点（記事 -2）は**意図的に二重**にしてある。
加点だけだと、出版社・ISBN が揃った記事に並ばれたとき順序が不安定になる。

### c. 候補選択後は ISBN で引き直す

検索 API の結果は詳細 API より情報が薄い（特に Open Library の
`search.json`）。候補に ISBN があれば詳細を取り直すことで、読み仮名や
訳者情報を回収する。これにより検索経由でも 50音順ソートが機能する。

### d. 手入力の導線を追加

§9.8-c で「取込失敗時に詰む」と指摘した問題への対処。検索で 0 件だった
場合は手入力パネルを自動で開き、入力済みのタイトル・著者を引き継ぐ。
読み仮名も入力でき、著者と件数が一致する場合のみ 50音順に使う。

### e. 検証

実データで確認した動作。

```
「地方創生を超えて」＋「小磯」 → 書籍が1位、講演録・座談会は下位
「中沢新一」のみ              → 20件（すべて図書）
「コミュニティ」＋「バウマン」   → 訳書2版、原著者と訳者を分離
「Gender Trouble」＋「Butler」 → Open Library から取得
```

回帰テストは 72 件に増やし、変異テストで以下がすべて検出されることを
確認した: 種別スコアの除去、図書/記事判別の無効化、手入力の姓名分割の
無効化、読み仮名の件数チェック除去。

## 9.11 弱点への対処（2026-08-02）

§9.8-d で挙げた 3 点に対処した。

### a. 検索性能 ― 最悪ケースで 78 秒かかっていた

**実測して初めて判明した重大な問題。** 通常の分布（2000 件）では検索 66ms で
問題なかったが、**全件が同じ語を含む場合**に破綻していた。

```
2000件・全件が「社会学研究」を含む場合
  "社会"        1656ms
  "社会学研究"  78683ms   ← 実用不能
```

原因は `anyOf(grams)`。bigram の **OR 検索**なので、検索語が長いほど
候補が増え、Dexie が重複走査を繰り返す。

検索語の**すべての** bigram を含むレコードだけが答えになりうるので、
どの bigram で絞っても正しい候補の上位集合が得られる。ならば
**最も候補数の少ない bigram 1 つ**で絞るのが最速になる（`narrowBy()`）。
件数は `count()` で数える（索引だけを見るので実データ取得より桁違いに速い）。

```
  "社会"        1656ms →  32ms
  "社会学研究" 78683ms →  36ms   （約 2200 倍）
```

回帰テストに性能検証を入れた（400 件・全件ヒットで 1500ms 未満）。
旧実装に戻すと 2655ms で落ちることを確認済み。

### b. 重複判定 ― 識別子だけでは防げない

同じ本を ISBN と DOI の双方から取り込むと 2 件になる。
`duplicateKey()`（筆頭著者の姓 + 出版年 + タイトルの主要部）で書誌の
内容から照合する。

副題（`:` 以降）を落とすのは、取得元によって副題の有無や区切り文字が
揺れるため（NDL は `書名 : 副題`、Open Library は `title` と `subtitle` が別）。

**自動では統合しない。** 改訂版・同名の別書・同姓同名の著者を誤って
同一視すると、ユーザーが気づかないまま別の文献が消える。候補を提示して
判断はユーザーに委ねる（「別の版なら登録、同じ本ならキャンセル」）。

年が無い書誌は判定対象外にする。除外しないと `|undefined|タイトル` という
キーになり、**年不明の文献同士が一致してしまう**。

### c. 和文／欧文の並び順切替

ロジックはあったが UI から到達できなかった（§9.8-c の指摘）。
執筆ページに選択欄を追加し、プロジェクトごとに `sortOrder` として保存する。

### d. 実測しないと分からなかったこと

a は「数百件を想定しているが実測していない」と自ら書いていた項目で、
実際に測ったら想定の 1000 倍遅いケースが見つかった。性能は推測ではなく
測るべきという例。

## 9.12 Next.js 移行（2026-08-03）

### a. 方針

| 項目 | 決定 |
|---|---|
| 型付け | UI のみ TypeScript。`src/` は JSDoc のまま |
| 既存 UI | `legacy/` に残す（比較用） |
| 配信 | `output: 'export'` で静的書き出し（サーバレスを維持） |

`src/` 2100 行は**一行も書き換えずに**そのまま動いた。JSDoc の型注釈が
TypeScript から解決できるため、型定義の二重管理も発生していない。

### b. ディレクトリの衝突

Next.js はルート直下の `app/` を app ディレクトリとして扱うため、
バニラ版の `app/` と衝突した。`web/app` に置く案は Next.js が認識しない
（`app` か `src/app` のみが規約）。`src/` は既にロジックで使っているので、
**バニラ版を `legacy/` へ改名**して解決した。

### c. 型チェックが捕まえた実際の不具合

移行の直接の成果。バニラ版では発見できなかったもの。

**1. `reference` が undefined になりうるのに参照していた（3 箇所）**

```
Type error: 'r.reference' is possibly 'undefined'.
```

取込結果は `ok: false` のとき `reference` を持たない。`if (!r.ok)` だけを
見て `r.reference.source` に触っており、取込失敗時に例外で落ちる経路だった。

**2. `r.error` が undefined の可能性**

候補 0 件のとき `ok: true` かつ `error: undefined` を返す仕様なので、
そのまま表示すると空文字になっていた。

### d. JSDoc の整備

型チェックを通す過程で、戻り値が `Object` / `Object[]` のままだった箇所を
具体化した（実装は変更していない）。

- `SearchCandidate` — 検索候補の形
- `ImportResult` / `ImportedReference` — 取込結果
- `StoredReference` / `StoredNote` / `StoredProject` — 永続化レコード
- `sortReferences` / `findMissingReadings` — ジェネリック化して入力の型を保つ

これによりエディタの補完も効くようになった。

### e. 静的書き出しでの注意

`useSearchParams` は Suspense 境界が必要（`/reference/` で `?id=` を読むため）。
境界が無いとビルドが失敗する。

Service Worker はビルド成果物のファイル名がハッシュ付きで変わるため、
レガシー版のような固定一覧を使えない。ハッシュを含まないパスだけを
事前キャッシュし、残りは実行時に拾う方式にした。

### f. 検証

- ビルド: 3 ページすべて静的生成
- 配信: `/`, `/reference/`, `/write/`, CSL 資産, SW, ZXing すべて 200
- 回帰テスト: 90 件通過（`src/` を変えていないので当然だが確認した）

## 9.13 独自ルール生成の実装（2026-08-03）

実装: `src/citation/overlay/`（samples / infer / apply）

§4 で方針を立て、§9.1 で MVP から外していた仕様 3.2-2 に着手した。
**推論エンジンは完成し、実文献への適用まで検証済み。UI への接続は未了。**

### a. 推論の実際

APU 形式のダミーを提示し、ユーザーが所属機関の形式へ直す。

```
提示  姓甲名甲・姓乙名乙・姓丙名丙（1999）『書名亜』社亜.
編集  姓甲名甲ほか，1999，書名亜，社亜．

推論  { etAlMin: 3, etAlUseFirst: 1, etAlTerm: "ほか",
        delimiter: "，", nameOrder: "family-given" }
```

実在の文献に適用した結果。

```
既定  小磯修二・村上裕一・山崎幹根（2018）『地方創生を超えて…』岩波書店.
独自  小磯修二ほか，2018，地方創生を超えて…，岩波書店．
```

### b. 番兵は CJK でなければならない

ダミーに識別用の文字列（番兵）を入れ、出力上の位置からフィールドを
確定する。文字列を解析して「ここが著者だろう」と推測しないのが精度の鍵。

**citeproc は名前の文字種で挙動を変える。** ラテン文字の番兵
（`zzFam1zz`）だと欧文名とみなされ姓名の間に半角スペースが入り、
和文の出力形を再現できない（実測で確認）。番兵は CJK にする必要がある。

### c. 文字列置換では足りない ― 型紙方式へ

当初は「『』→ 空文字」のような出力置換で表現しようとしたが破綻した。
囲みを外すと、代わりに現れる区切り（「，」）を補えない。

```
置換方式  姓甲名甲1999書名亜社亜．     ← 区切りが入らない
型紙方式  姓甲名甲，1999，書名亜，社亜．
```

フィールドの並び順と、その間の文字列を型紙（layout）として保持し、
値を差し込んで組み立て直す方式に変えた。書籍と論文でフィールドが違うため
型紙は種類ごとに持つ。

### d. 誤推論を避ける三つの歯止め

推論を誤ると**ユーザーが気づかないまま全文献の書式が壊れる**。
確信が持てないときは推論しないことを優先した。

1. **矛盾の検出** — 「2名は省略、3名は省略せず」のような不整合があれば
   境界が定まらないので推論を諦める
2. **全行一致の要求** — 行ごとに違う書式が出た要素は採用せず、
   `conflicts` として報告する
3. **省略の対象を限定** — 著者が複数で対応が取れないときは変換しない

### e. 検証ループ

推論した規則を全ダミー行に再適用し、ユーザーの編集結果を再現できるか
確かめる（設計書 §4.4 のステップ4）。5/5 一致を確認済み。

さらに**ダミーではない実文献**にも適用して検証した。ダミーだけで一致しても
実データで壊れては意味がないため。

### f. テストの穴を変異テストで発見

当初、3 件の変異が検出できなかった。原因はいずれもテストデータの不備。

| 変異 | 原因 |
|---|---|
| 矛盾チェックの除去 | 用意した「矛盾データ」が実は省略として検出されておらず、矛盾チェックに到達していなかった |
| 全行一致の判定除去 | 書式が割れるケースを試していなかった |
| 空フィールドの読み飛ばし除去 | 出版社の無い書誌を試していなかった |

いずれもテストを足して検出可能にした（118 件）。

### g. UI への接続（2026-08-03 完了）

`/style` ページを追加し、推論の全工程を通した。

1. ダミーを既定スタイルで提示（著者1/2/3/5名 + 論文）
2. ユーザーが所属機関の形式へ直す
3. 「規則を読み取る」で推論し、実文献でプレビュー
4. 「この規則を使う」で保存（settings の `customOverlay`）

保存すると `styleId: 'custom'` になり、引用文献リストに反映される。

**再現できない編集は保存させない。** 推論した規則を全ダミー行へ再適用し、
ユーザーの編集と一致しない行があれば「入力 / 結果」を並べて示す。
誤った規則を保存すると全文献の書式が壊れるため、ここで止める。

**プレビューは overlay 経由に統一した。** `styleId` が `'custom'` のとき
`engine.renderOne` を直接呼ぶと「未知のスタイル: custom」で例外になる
（実測で確認）。書架・文献詳細の両プレビューを `renderWithOverlay` に通した。

### h. 型紙の無い種類はフォールバックする

ダミーは書籍と雑誌論文だけ。章・ウェブ・学位論文には型紙が無い。

当初 `container-title` の有無で論文と判定していたため、章を論文の型紙に
当てて「グローバル社会の課題)」と**閉じ括弧だけが残る壊れた出力**になった
（実測で確認）。`csl.type` で厳密に判定し、対応しない種類は既定スタイルへ
フォールバックするよう修正した。

一覧に型紙の無い文献が混ざった場合は**全件フォールバック**する。
一部だけ独自形式になると書式が不揃いなリストが出てしまうため。

### i. 残る制約

- 欧文文献のダミーが無い（和文のみ）。欧文書誌は既定スタイルで出る
- 章・ウェブサイト等の独自ルールは作れない
- 推論結果はアプリ全体で1つ（プロジェクトごとに別の独自ルールは持てない）

**背景.** APU 固有の規定が 6 か所へ散っていた。CSL、本文中の引用の型
（`intext.js`）、種別ごとの入力欄（`src/import/reftypes.js`）、
一覧のぶら下げ幅と引用の下げ幅（`export.js` に `4em` / `2em` 直書き）、
URL 前の改行幅（`engine.js` に全角4字直書き）、並び順の既定
（`sort.js` の `'ja-first'`）。この状態で 2 つ目の方式を足すと、
数値の直書きが全て APU の規定のまま効いてしまう。

**構成.** 1 方式 = 1 ディレクトリにまとめた。

```
src/citation/styles/
  types.js          パッケージの取り決め（JSDoc 型のみ）
  index.js          登録簿。方式を足すときに触る唯一のファイル
  apu/
    style.csl       書式
    intext.js       本文中の引用の型（2章・3章・7章）
    reftypes.js     種別と入力欄（5章・9章）
    index.js        上をまとめた定義
```

CSL で表せない規定（`layout` / `sort`）も同じパッケージに置く。
出力側に固定値として持たせると 2 つ目で破綻するため。

汎用層（`intext.js` / `reftypes.js` / `export.js` / `sort.js`）は
`styleOf(styleId)` 経由で値を引くだけにした。本文中の引用の組み立ても、
出典表記を部品（著者名・年・ページ）へ分けるところまでを汎用層が担い、
地の文との組み方は各方式の `build()` に委ねる。

**検証.** 「アプリ側に触れずに方式を足せるか」を実際に試した。
apu を複製した `probe` を登録簿へ 1 行足してビルドしたところ、
CSL の配信・Service Worker の先読み一覧・スタイル選択 UI が
自動で追随した。確認後に撤去してある。

テストでは合成スタイル（下げ幅 1 字 / 3 字、閾値 5 字、`en-first`）を
登録簿へ差し込み、出力が実際に追随することを確かめている。
この検証で **登録簿の索引を作り置きしていた不具合**（`STYLES` へ足しても
`styleOf` が引けない）が見つかり、毎回参照する形へ直した。

**残っていた直書き.** 執筆ページが並び順の既定を 'ja-first' と直書きしており、
パッケージの `sort.defaultOrder` を無視していた。`styleOf(styleId)` から
引くよう直した（利用者が画面で選び直していればそちらが勝つ点は従来どおり）。

**併せて直したもの.** Service Worker の CSL 先読み一覧を手書きから
ビルド時生成（`BUILD:STYLE_ASSETS`）へ変更した。手書きのままだと
方式を足したときに列挙し忘れ、その端末だけオフラインで開けなくなる。
CSL の配置が `styles/<id>/style.csl` へ変わったため `VERSION` も上げた。

### 9.16 取込のタイムアウト（2026-08-03）

**背景.** 公開後の検証で NDL の初回応答に 12.5 秒かかった（2 回目以降は
0.06 秒。コールドスタートと思われる）。これを機に調べたところ、
取込コードに**タイムアウトが一切無かった**。API が無応答になると
画面が固まったまま戻らず、利用者には中断する手立てがない。
大学の回線で十分起こりうる。

**実測した応答時間.**

| API | 通常 | 備考 |
|---|---|---|
| NDL | 0.05 秒 | 初回のみ 12.5 秒 |
| Crossref | 0.6 秒 | |
| Open Library | 1.0 秒 | |

**方針.** `src/import/http.js` に共通の `fetchWithTimeout` を置き、
4 か所（ISBN・DOI・NDL 検索・Open Library 検索）すべてを通した。

- 1 API あたり **12 秒**。通常の応答時間から見て十分な余裕がある。
  これ以上延ばしても成功率はほとんど上がらず、待たされる不快さが増える
- ISBN 取込は 2 つの API を順に試すため、1 件ごとの制限だけでは
  最悪 2 倍待つ。**全体の上限 18 秒**を別に設け、残り時間を割り当てる
- `AbortSignal.timeout()` は使わない。Safari 16 未満の iOS でも
  動かす必要があるため `AbortController` を自前で回す

**時間切れと通信失敗を区別する.** 利用者への案内が変わるため
（前者は「時間をおいて」、後者は「接続を確認」）。特に ISBN 取込では、
時間切れを「見つかりませんでした」と伝えてはいけない。実際には
存在する本で、あとで試せば取れる可能性が高い。

**Crossref の時間切れは再試行しない.** 429/5xx は従来どおり 3 回試すが、
時間切れで同じ回数を繰り返すと 3 倍待たせることになる。
通信エラーの再試行は従来どおり残してある。

**検証.** 応答しない `fetch` を渡して、打ち切られること・文言が正しいこと・
全体の上限が効くことを確認し、テストへ固定した（10 件）。
さらに `ctrl.abort()` を無効化する変異を注入したところ、
**テストが無限に停止**した（＝検出できている）。

### 9.17 アプリ内の使い方ページ（2026-08-05）

試験運用にあたり、`/help` を追加した。ナビに「使い方」として並べる。

**出力例を直書きしない.** 引用の例（本文中の引用・引用文献リスト）は
文字列で持たず、画面で引用エンジンに実際に作らせている。直書きすると
書式を直したときに例だけ古くなり、「説明と実物が違う」という
最もたちの悪い状態になる。見本の書誌は `app/help/page.tsx` に置いた。

**書き方.** 読み物ではなく作業の手引きなので、画面のボタン名を
そのまま出す（`.uikey`）。手順は「どの画面での作業か」を見出しに添え、
書架と執筆のどちらを開けばよいか迷わないようにした。

**内容の要点.**

- 冒頭で「書架」と「執筆」の役割の違いを示す。ここが分かれば迷わない
- 取込は 3 方法を上から順に（検索 → ISBN/DOI → 手入力）
- 「応答がありません」が**文献の不在を意味しない**ことを明記した
  （§9.16 のタイムアウト対応で出るようになった文言）
- データが端末内にのみ保存されることを繰り返し書く。
  別端末で空なのは仕様だが、説明が無ければ不具合に見える
- 最後に「提出前に必ず自分の目で確認」を置く。ツールを過信させない

**検証.** 例が空や壊れた形にならないことをテストへ固定した（6 件）。
型の `build()` を壊す変異を注入し、検出できることを確認済み。
オフラインでも読めるよう SW の先読みに `/help/` を加え、VERSION を上げた。

### 9.18 訳書の原著者名と、抜き書きの一括書き出し（2026-08-05）

**a. 訳書の原著者は「ルーマン, N.」**

利用者から実例の提示があり、訳書の原著者名に読点が要ることが判明した。

    ルーマン, N.（1990）『信頼 : 社会的な複雑性の縮減メカニズム』大庭健・正村俊之訳，勁草書房.

和文の姓名は「田中太郎」と続けるため、和文分岐は `sort-separator=""`
にしてある。しかし訳書の原著者はカタカナ表記の欧文名で、
姓と名（頭文字）の間に読点が要る。

**CSL では解決できなかった。** citeproc はカタカナ姓を CJK 名と判定し、
`sort-separator=", "` を明示しても無視して空白で繋ぐ（最小の CSL で切り分けて確認）。

| 著者 | 出力 |
|---|---|
| ルーマン + N. | ルーマン N. ← 区切りが効かない |
| Luhmann + N. | Luhmann, N. |
| 田中 + 太郎 | 田中太郎 |

そこで一覧へ渡す直前に `literal` へ畳む（`foldTransliteratedNames`）。
対象は「訳者がいる」かつ「姓がカタカナのみ」かつ「名にラテン文字を含む」もの。

**本文中の出典表記には適用しない。** `literal` には short 形が無く、
「（ルーマン, N., 1990）」になってしまう。姓のみで正しいので、
`renderBibliography` の中だけで畳み、`renderCitation` は素のまま使う。

マニュアルに訳書の規定は無く、§9.6-f に「実運用で確認が要る」と
残していた項目。今回の実例で確定した。

**b. 抜き書きの一括書き出し**

1 つの文献に溜めた抜き書きを、すべて `「〜〜」（著者, 年, p.数）。` の
形に揃えて出す（`src/citation/quotes.js`）。1 件ずつコピーするより、
まとめて下書きへ流し込んでから削るほうが早い。

- 出典表記は引用エンジンに作らせる。文字列連結だと p./pp. の
  使い分けや同一著者・同年の a/b/c が落ちる
- **ページ数の無い抜き書きは出さない。** 直接引用はページ数が無いと
  引用として成立しない（マニュアル 2.1）。黙って出すと不完全な引用が
  そのまま本文へ移る。除外件数は画面に知らせる
- コメントを添える指定ができる。引用と自分の言葉は色と字下げで分ける。
  混ざったまま転記されると剽窃になりかねない

**検証.** 両方をテストへ固定した（15 件・計 211）。
畳み処理を無効化する変異、ページ無しを出力してしまう変異の
いずれも検出できることを確認済み。

### 9.19 抜き書きの並べ替え（2026-08-05）

抜き書きが溜まると、読んだ順に見たいときと、本の頭から追いたいときが
出てくる。6 通りの並べ替えを付けた（`src/db/notesort.js`）。

| 並び | 用途 |
|---|---|
| 登録が新しい／古い順 | 読み返すとき |
| ページの小さい／大きい順 | 本文を順に追うとき |
| コメントが新しい／古い順 | 自分の考察を辿るとき |

**ページは必ず数値で比べる.** 文字列比較だと「7」が「12」より後に来る。
範囲（`12-14`）は開始ページで見る。数字を含まないものは末尾へ回し、
**昇順・降順のどちらでも末尾**に置く。降順で先頭に来ると、
本文を追う目的で並べたのに関係ない項目が最初に出てしまう。

**コメント順のために `commentAt` を足した.** `updatedAt` はページ数の
修正でも動くため、「コメントを付けた順」には使えない。
コメントの中身が変わったときだけ打ち直し、消したら時刻も消す。

既存データは `commentAt` を持たないので、`listNotes` で `updatedAt` から
補う。正確ではないが、並べ替えたときに旧データだけ末尾へ固まるより良い。
索引に使わない項目なのでスキーマ変更（version 2）は不要だった。

並べ替えは一括書き出しの順にもそのまま効く。画面で見えている順と
書き出される順が違うと戸惑うため。

**検証.** 12 件をテストへ固定（計 231）。ページを文字列比較に戻す変異と、
`commentAt` を `updatedAt` と同じにする変異の両方を検出できることを確認済み。
